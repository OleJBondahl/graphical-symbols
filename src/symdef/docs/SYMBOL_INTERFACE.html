Symbol interface design guide

Binding spec for the graphical-symbols toolkit and the iec60617 data repo. Agreed with the repo owner on 2026-09-19. Identical copies live at docs/SYMBOL_INTERFACE.html in both repos; change both together.

This guide is the only design document. The earlier docs/DESIGN.md and docs/superpowers/plans/ in both repos described a Python-factory design and have been removed; they exist only in git history and must not be revived. Code already in graphical-symbols was built from that older design and is to be reworked to match this guide (see section 13). This is a from-scratch design: nothing in Schematika's symbol code is a constraint.

1. Why: what went wrong before

Schematika's symbols made one object do three jobs. Every recurring problem traces back to that.

LayerWhat it isExampleOwner
Symbolthe graphic concept in the standardmake contact, S00227data repo (iec60617)
Device terminal markingnumbers printed on the real part (EN 50005 / EN 50011)13/14, 23/24, A1/A2the consumer's device or catalog model
Placementtag, position, orientation, rendered text-K1 at (40, 120)the drawing library
  • Port identity drifted. no_contact() had ports 13/14, no_contact(poles=2) had 1/2/3/4, and keys were remapped after construction. Resolvers broke on ids that were not port keys.
  • Text was baked into geometry. Tags and pin numbers were text elements placed by heuristics, so layout could not tell label space from body space and labels collided.
  • Wiring geometry was per-symbol luck. No shared port pitch, no guaranteed straight-through axis, no guaranteed clear exit for a wire.
  • Variants were hand-written geometry. inverted=True, multi-pole and contact-plus-actuator forms each copied coordinates, so a correction had to be repeated everywhere.
  • Electrical function lived in docstrings. Every consumer re-encoded "these four ports are one net" and "this is a switch".

2. Principles

  1. A symbol is a definition. It has no tag, no terminal numbers, no position and no orientation. Those belong to the placement.
  2. Port ids are roles. Stable, lowercase, semantic, never terminal numbers, never dependent on configuration.
  3. Electrical function is data. Nodes and typed paths, so consumers netlist and check without per-symbol knowledge.
  4. Text goes in slots. The symbol reserves boxes for the tag and for each port's marking. The consumer renders the text.
  5. Data is the source of truth. One TOML file per symbol, validated by a published JSON Schema. Any language can consume the resolved JSON.
  6. Composition mirrors the standard. IEC 60617 builds symbols from elements and qualifying symbols. Composites reference parts by anchor and contain no copied coordinates.
  7. The wiring contract is strict and linted in all 8 orientations. A router never repairs a symbol.
  8. Every gate is proven able to fail with a deliberately broken fixture.

3. Conventions

ItemRule
UnitThe module M. Default M = 2.5 mm (ISO 81714-1, ISO 14617). Files never contain millimetres.
AxesSVG axes: x right, y down. Angles in degrees, clockwise on screen from +x.
Drawing grid0.125 M. Every shape coordinate, radius, text height, anchor, slot point and slot box size is a multiple of it. 0.125 is exact in binary floating point.
Wiring grid1 M. Every port position is a multiple of it. The origin is on it by definition.
Pole pitch4 M (10 mm). The only pitch repeat uses by default. A symbol too wide for it declares pole_pitch, a multiple of 4.
Same-side port spacingTwo ports with the same dir are a multiple of 2 M apart, measured along the side (x for N and S ports, y for E and W ports).
Base orientationThe through path (section 5) is vertical: its two ports are at (0, -a) pointing N and (0, a) pointing S, with a a whole number of M. Horizontal use is an orientation, never a second file.
Line weightnormal = 0.1 M (ISO 81714-1, width : module = 1 : 10), thick = 0.2 M (provisional).
Line stylesolid or dashed. Dashed means dash 0.5 M, gap 0.25 M; renderers implement the pattern, files never spell out dash segments.
Text elementsText that is part of the symbol itself (the M in a motor). Height at most 1 M. Stays upright in every orientation; only its position transforms.
ExtentsAll boxes ignore stroke width. A line or polyline extends over its points, a circle over its full diameter, an arc over its true swept extent. A text element counts as a box centred on at, height tall and 0.6 × height × character count wide.
OverlapTwo shapes overlap when their open interiors intersect. Touching along an edge or at a corner is not overlap. For overlap tests a stroke is a zero-width curve, a filled shape is its area, and an unfilled closed outline is only its outline (so a slot may sit inside an empty body rectangle).
IdsPort, anchor and part ids match ^[a-z][a-z0-9_]*$. The dot is reserved for namespacing by composition and repeat (contact.in, 2.out).

Orientations

There are exactly 8: R0 R90 R180 R270 MR0 MR90 MR180 MR270. M mirrors first (flip x: (x, y) -> (-x, y)), then Rn rotates clockwise on screen by n degrees. A 90 degree clockwise rotation is (x, y) -> (-y, x). Directions and slot sides transform the same way as vectors. Circle and arc centres transform as points and radii are unchanged. Rotation by n adds n to an arc's start and end. Mirroring maps an angle t to 180 - t and swaps start with end, so the arc is still swept clockwise. Angles are normalised to [0, 360). Text elements and slot boxes never rotate or mirror; only their at point moves. Flipping top to bottom is MR180. There is no other transform in the interface.

Port id vocabulary

CaseIds
Any two-terminal series symbol (contact, fuse, resistor, coil, lamp)in (top in base orientation), out. No polarity is implied.
Polarity carries meaninganode/cathode, plus/minus
Change-over contactcom, nc, no

A1/A2, 13/14, X1/X2 are terminal markings, not roles. They never appear in a symbol file. Generic consumers should chain symbols using the through path's from and to, not by assuming the ids in/out.

4. The symbol file

One file per symbol: symbols/<number>.toml in the data repo. Symbol elements and qualifying symbols from IEC 60617 Part 2 are files too, with a different kind.

The examples in this guide are normative for the format and have been machine-checked: they parse as TOML, every reference resolves, and the four atomic ones pass port-off-geometry, port-on-body-edge, port-lane-clear, port-spacing, through-axis, slot-overlap-body, slot-overlap-slot, pitch-overflow and allow-unused in all 8 orientations, using a throwaway checker written from the definitions in this guide. The toolkit's first test fixture is these five files: they must load and lint clean. If the real linter disagrees with an example, stop and resolve which one is wrong before going on. The shapes themselves are unverified against IEC drawings, like all geometry.

5. Connectivity model

This is what keeps the electrical function explicit. It is declarative data only; the toolkit never simulates anything.

  • Node. A set of ports that are the same electrical point inside the symbol. Every port belongs to exactly one node. A port not listed under nodes is a node of its own. Ports may share a position only if they share a node.
  • Node potential (optional): earth, protective_earth, functional_earth, frame. This is how an earth symbol says what it does: nodes = [{ ports = ["pe"], potential = "protective_earth" }].
  • Path. A two-terminal relation between ports of two different nodes, with a kind. At most one path per unordered node pair.
  • Through path. At most one path per symbol has through = true. It is the axis series chains run along, and it fixes the base orientation: from is the N port, to is the S port. A kind = "symbol" file with two or more nodes and no potential should have one.
Path kindMeaningDirection mattersExamples
conductoralways conductsnofuse, link, shunt
switch_openopen in the drawn (rest, de-energised) statenomake contact, circuit breaker
switch_closedclosed in the drawn statenobreak contact
impedancea load or passive element: consumes or storesnoresistor, capacitor, coil, lamp, motor winding, meter
sourcedelivers energy; to is the positive terminal where polarity existsyesbattery, generator
diodeconducts from from to to onlyyesdiode, LED, thyristor main path

What a consumer can do with this and nothing else: build a netlist across placed symbols, find nets with a source and no load, find nets that are shorted through conductors, trace which switch states complete a circuit, and know that a terminal's or junction's ports are one net. Tag letter codes (IEC 81346) and device behaviour stay in the consumer: they classify devices, not symbols.

6. Text slots and boxes

A slot reserves room for text the consumer will draw. A symbol never contains tag or marking text.

SlotMeaning
tagThe reference designation (-K1). Required for kind = "symbol".
"marking.<port id>"The terminal marking for that port (13). Required for every port of a kind = "symbol" file.
valueOptional. Rating or value text (10 A).

Each slot is { at = [x, y], side = "N|E|S|W", box = [w, h] } with w and h positive. Text is always upright. side says which way the box grows from at, and therefore the alignment:

sideBox, for at = (x, y), box = [w, h]Text alignment
Ex in [x, x + w], y in [y - h/2, y + h/2]start, vertically centred
Wx in [x - w, x], y in [y - h/2, y + h/2]end, vertically centred
Nx in [x - w/2, x + w/2], y in [y - h, y]middle, sitting above at
Sx in [x - w/2, x + w/2], y in [y, y + h]middle, hanging below at

Orientation. at transforms as a point and side as a direction. box stays [w, h], because the text stays upright. So one declaration covers all 8 orientations, and because the box does not rotate with the symbol, slot rules must be linted in every orientation, not just the base one.

Two boxes for layout engines. body_box is the extent of the elements. keepout_box is the body box united with every slot box. A layout engine that keeps keep-out boxes apart can never produce a label collision between symbols.

Consumer duty. The box is a maximum extent. A consumer that draws text larger than the box has broken the contract on its side; it should shrink or report, never overflow silently.

7. Composition

Parts

A composite lists parts. Each part is { as, use, ... }: a local id and the number of another file.

KeyMeaning
asLocal part id. Namespaces the part's ports, anchors and slots: contact.in.
useReference number of the part's file. Any kind.
orientOptional orientation applied to the part before placing. Default R0.
attach, to, length, viaPlace by anchor. The part's anchor attach is put at the point length M from the target anchor to ("part.anchor"), along the target's direction. The two anchors must face each other after orient; otherwise it is a lint error. via = "mechanical_link" adds a dashed line between them. length defaults to 0, via to none.
atAlternative to attach: place the part's origin at [x, y]. For qualifiers drawn inside a body. The first part defaults to at = [0, 0]. Every later part must have exactly one of attach or at.
repeatOptional pole count. Applied to the part first, before orient and placement. Its ports are then part.1.in, part.2.in, and so on.

Placement, exactly. Parts are resolved in file order, and to may only name an anchor of an earlier part. Let T and dT be the target anchor's position and unit direction in the composite's frame, and A and dA the attaching anchor's position and direction in the part's own frame after repeat and orient. It is an error unless dA = -dT. The part is translated by T + length × dT - A. With via = "mechanical_link" the composite gains the element { line = [T, T + length × dT], style = "dashed" }; length must then be positive. The flattened result is linted like any other symbol, so a placement that pushes a port off the wiring grid fails there.

What a composite inherits

  • Ports: only through the explicit rename map ports = { new = "part.port" }. Every port of every part must be exported. There is no implicit export.
  • Nodes and paths: inherited automatically through the renames. A path declared in the composite's own paths replaces the inherited path between the same nodes. If more than one inherited path is marked through, the composite must redeclare the one that stays; the through flag is then cleared on all the others.
  • Anchors: not inherited. A composite declares its own if it is meant to be a part.
  • Slots: not inherited silently. A slot value may be a string reference ("marking.in" = "contact.marking.in") or a new table. A part's tag slot is usually where the next part goes, so composites normally declare a new tag.
  • Elements: all parts' elements, plus the composite's own elements if present.

S00171 stands for the Part 2 qualifier "operated by pushing". Its number, like every number in this guide, must be confirmed against the IEC database overview before the file is committed.

repeat: the only multi-pole mechanism

repeat(symbol, n) places n copies along +x in base orientation and returns an ordinary symbol. Pole k (counting from 1) is the symbol translated by ((k - 1) × pitch, 0), where pitch is the symbol's pole_pitch, default 4. It requires n >= 1 and a symbol with a through path; repeat(symbol, 1) still renames the ports.

  • Ports, and their marking slots, are prefixed with the pole number: 1.in, 2.in, "marking.2.in". Nodes and paths repeat per pole. Pole 1's through path stays the through path; the flag is cleared on the other poles. The result's pole_pitch is n × pitch.
  • The tag slot is taken from pole 1 only. A value slot likewise.
  • If the symbol has an anchor with the id link and n > 1, the result gains one element: a dashed line from pole 1's link anchor to pole n's. It may cross the poles in between; that is how the standard draws it. Pole 1's anchors become the result's anchors; the other poles' anchors are dropped.
  • It is available as a toolkit function for consumers, and as a data op in a part: { as = "main", use = "S00227", repeat = 3 }.

There are no poles=, pins= or inverted= parameters anywhere. Pole count is repeat, markings belong to the placement, and inversion is the orientation MR180.

8. Wiring contract

What every flattened symbol guarantees a router, in all 8 orientations:

  1. Every port is on the 1 M wiring grid.
  2. Every port is the free end of a lead (or lies on the outline) and sits on the side of the body_box that matches its direction. Its direction is that side's outward normal.
  3. The wire lane of every port is clear. For a port at P with direction d, the lane is the open, unbounded region of points P + t × d + u × n with t > 0 and |u| < 0.25, where n is perpendicular to d. No element and no slot box overlaps it. The port's own lead ends at t = 0 and a marking box 0.25 M beside the wire only touches the lane, so both are fine. A wire that leaves a port straight crosses nothing of its own symbol.
  4. The through path is collinear on x = 0 with ports at (0, -a) and (0, a). Series chains wire dead straight, and chained symbol heights are whole M.
  5. Same-side ports are a multiple of 2 M apart, and repeated poles are 4 M apart, so a 3-pole breaker, a 3-pole contactor and a motor's u v w line up without jogs.
  6. For a symbol with a through path, the x extent in base orientation of the body box united with every slot box except tag and value is at most its pole pitch, so repeated poles never overlap each other.

A symbol that cannot comply declares each exemption in lint_allow with a reason. An exemption whose rule would not have fired is itself an error, so exemptions cannot rot.

9. Lint rules

lint(symbol) runs on a flattened symbol and returns findings: rule, severity, message, optional location, optional orientation. Geometric rules run in all 8 orientations. Composition rules run in the resolver and are reported the same way. All are errors unless marked. Data repo gates require zero findings of either severity, so a warning is simply a finding that more often deserves a lint_allow entry; exemptions work the same for both. slot-missing, through-missing and pitch-overflow apply only to kind = "symbol"; every other rule applies to every kind.

10. Resolved output

The build flattens every file and writes JSON. This is the interface for consumers that are not Python, and for simple consumers of any kind: they never implement composition.

  • build/resolved/<number>.json: one flattened symbol. Same schema as the source, with parts gone, composite ports expanded to the array form, slot references expanded to tables, nodes listing every node explicitly, and two computed keys: body_box and keepout_box, each [[min_x, min_y], [max_x, max_y]] in base orientation.
  • src/<package>/bundle.json: the bundle, shipped as package data: { "schema": 1, "standard": "IEC 60617", "symbols": { "S00227": { ... }, ... } }. It is generated and tracked like build/, and stale_build covers it.
  • Output is deterministic: UTF-8, LF line endings, 2-space indent, object keys sorted, arrays in source order, a whole number written without a decimal point and any other number in its shortest exact decimal form, one trailing newline. A symbol change shows up as a reviewable diff.

A consumer in another language needs the bundle, the schema, and the orientation and slot-box rules from sections 3 and 6. That is about thirty lines of code.

annotate=True draws the grid, ports with ids and lanes, anchors, slot boxes, and both boxes. texts maps slot ids to sample strings so the gallery can show a filled-in symbol.

The data repo's Python package is a thin wrapper: from iec60617 import LIBRARY, loaded from the bundled JSON shipped as package data.

What a drawing library does

from graphical_symbols import Orientation, keepout_box, orient, repeat
from iec60617 import LIBRARY

breaker = orient(repeat(LIBRARY.get("S00287"), 3), Orientation.R0)

# The placement is the consumer's own type. The symbol stays a definition.
placed = Placement(
    symbol=breaker,
    at=Point(40, 120),
    tag="-Q1",
    markings={"1.in": "1", "1.out": "2", "2.in": "3", "2.out": "4", "3.in": "5", "3.out": "6"},
)
  • Layout keeps keepout_box rectangles apart and aligns through axes.
  • Routing starts each wire at a port, along its direction. The lane is guaranteed clear.
  • Text is drawn into slot_box(slot) with the alignment given by the slot's side.
  • Netlisting and checks read nodes and paths.
  • Markings are keyed by port id. The keys are validated against the symbol's ports, so a marking for a port that does not exist fails loudly at placement.

The toolkit knows nothing about any standard. Everything standard-specific is in the data repo's library.toml:

standard = "IEC 60617"
title = "IEC 60617 symbols"
number_pattern = '^S\d{5}$'

[vocabulary]
path_kinds = ["conductor", "switch_open", "switch_closed", "impedance", "source", "diode"]
potentials = ["earth", "protective_earth", "functional_earth", "frame"]
links = ["mechanical_link"]

[rules]
required_slots = ["tag", "marking.<port>"]

Later standards (ISO 14617, ISA 5.1) are sibling data repos that reuse the toolkit and every gate.

Gates in a data repo (just ci)

  • Every file validates against the schema and resolves.
  • Every flattened symbol lints with zero findings, warnings included, in all 8 orientations.
  • Every symbol with a through path also lints clean as repeat(symbol, 3).
  • stale_build reports nothing, so build/ always matches symbols/.
  • Reference numbers are unique, match the standard's pattern and equal the file stems.

Gates in the toolkit

  • Every lint rule has a fixture that makes it fire.
  • orient round-trips: applying an orientation and its inverse returns the same symbol (property test).
  • The five example files in this guide load and, once the rules exist, lint clean.
  • The JSON Schema and the Python loader agree: a file accepted by one is accepted by the other (fixture-driven).

Constraints carried over

Python >=3.14, uv only, every dependency pinned to the exact latest stable version, ruff, ty, pytest with hypothesis, vulture, deal. TOML is read with the standard library's tomllib. Geometry is unverified until compared with the IEC database drawings; the gallery shows the status next to each symbol.

13. What survives from the existing code

As of 2026-09-19 graphical-symbols contains units.py, geometry.py, symbol.py, transform.py and svg.py, built from the older design. iec60617 contains no code.

  • Keep: units.py (snap, on_grid), the geometry primitives, Direction, Box, the arc-extent logic in bbox, Reference, Status, the affine point, direction and arc-angle mapping inside transform.py, the element rendering inside svg.py, the toolchain, the purity gate and the justfile.
  • Rework: Symbol and Port gain the fields in section 11. Elements gain style. bbox becomes body_box and counts text by the extent rule in section 3. The public rotate and mirror are replaced by the single orient, which must also carry nodes, paths, anchors and slots; translate stays. to_svg's annotated mode gains lanes, anchors, slot boxes and both boxes.
  • Never build: Python symbol factories, a kit module, a dashed_line helper (dashed is a line style), a Registry of factories, or a Ports: docstring convention. The symbol file is the documentation.

14. Deferred and open

  • Coupling between paths (a coil actuating contacts, magnetically coupled windings). In detached representation this lives between separately placed symbols, so it belongs to the consumer's device model. Revisit for attached composites such as a contactor drawn as one symbol.
  • Conventional marking hints. EN 50005 function digits (make = 3/4, break = 1/2, change-over = 1/2/4) could be optional per-port data so consumers without a catalog get sensible defaults. Not in schema 1.
  • Connections between parts inside a composite (merging two parts' nodes). Not needed for IEC composites found so far.
  • Small symbols such as the terminal (S00017), whose natural port positions are on a 0.5 M circle. Decide per symbol: leads to the wiring grid, or a declared exemption as for the connection point.
  • Reference numbers quoted here (S00230, S00171, S00287) come from memory of the IEC database overview and must be confirmed before use.
  • Verification. The IEC drawings are behind a subscription. Until bought, every symbol stays unverified.
